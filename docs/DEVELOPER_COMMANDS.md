## Current development and Consultant runtime

### Disposable database requirement (MB-UX-QUALITY-001 L06)

Tests must never target the saved-user database `matchbase_slice1`. The shared pool factory rejects that name before connecting in Node, directly invoked test files, Vitest and explicitly guarded browser/child processes, even when a disposable marker is supplied. Production migration behavior is unchanged.

The canonical `Build` action in `C:/INNOBASE/MatchBASE/03_Implementation/INNOBASE-MatchBASE/deployment/local/Manage-LocalDocker.ps1` creates a temporary PostgreSQL container with a loopback-only random port, tmpfs storage and database `matchbase_test`. It clears inherited database/provider settings for the test process, sets the approved disposable endpoint, runs the full host unit gate and removes its owned container. GitHub CI uses its own ephemeral `matchbase_test` service. These are distinct from the running product database and its volumes.

Manual HTTP `test-*` scripts also require `MATCHBASE_DISPOSABLE_TEST_BASE_URL`: an explicit loopback HTTP origin on a non-runtime port. Ports 3000 and 3001 are refused; optional `BASE_URL` must match that origin. Build the data package first, then start an isolated web server against the same disposable database before setting this marker. The marker declares the operator-owned target; it does not remotely prove the server's database binding. Requests cannot leave that origin or automatically follow redirects into the running product. DB-only manual test scripts enter the same database guard through the shared script resolver.

For manual database or local browser tests, first provision an independently owned loopback-only PostgreSQL instance with database `matchbase_test`. Clear inherited runtime database and provider credentials. Set `DATABASE_URL`, `MATCHBASE_DATABASE_URL`, `MATCHBASE_CONSULTANT_TEST_DATABASE_URL` and `MATCHBASE_DISPOSABLE_TEST_DATABASE_URL` to that same temporary endpoint, and set `MATCHBASE_TEST_DATABASE_GUARD=required`. A marker does not authorize the saved-user database. The guard checks the actual pool target against the declared host, port and user; it rejects remote hosts, URL connection overrides, ambiguous targets and unrelated databases. Isolated UUID-suffixed test databases and the control database `postgres` are allowed only on that same disposable instance. Protocol/readiness fixtures explicitly declare their owned loopback fake endpoint instead.

`C:/INNOBASE/MatchBASE/03_Implementation/INNOBASE-MatchBASE/playwright.config.mjs` applies this guard before starting any migration, seed or web server, strips inherited provider keys and passes the guarded endpoint into child services. Custom browser configurations need the same explicit guard and owned disposable endpoint; intercepted HTTP routes alone do not isolate a server's database. Omitting database settings can skip PostgreSQL-dependent unit tests and must be reported as skipped coverage. Supplying an unsafe database fails the run instead of skipping it. Pure safety regressions run without PostgreSQL: `node --test test/slice1/data/test-database-safety.test.mjs` after building `@matchbase/data`.

The root local runtime scripts manage only their own PID/instance records. `START ... -Restart` drains the Consultant worker before relaunch. Web/Both stop or restart requires an operator-confirmed idle web application: Next dev does not guarantee active HTTP/after-callback draining on Windows, and the scripts do not automatically check database idleness. They never stop a database, kill a process merely because it uses a port, or read a credential file. Their heartbeat reports process liveness; database job/event inspection establishes worker progress.
